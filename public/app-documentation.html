I Understanding the app

01 · What this app is

In one sentence, and then in detail.

★ The one-sentence version

This is a single-page marketing website for a software engineering business. Its one job is to make a visitor trust you enough to send you a message. It does that by showing your real work in detail, letting them price their own project in two minutes, and then capturing their brief as a real email in your inbox.

What it actually does

  • Presents you. A headline, a short pitch, four credibility badges, and a live availability badge at the top of the page.
  • Proves the work. Five detailed case studies, each with the problem, the engineered solution, the business result, the technology used, and a clickable live preview of the real thing.
  • Explains the process. A four-step delivery roadmap, a client protection guarantee, and two testimonials.
  • Prices the work. A working calculator that produces a real price range and timeline in two currencies, from your own data — not a "contact us for pricing" dead end.
  • Captures the lead. A booking button that opens your live calendar, a WhatsApp button, and a contact form that sends a formatted email to your inbox.

What it deliberately does not do

Understanding the boundaries saves a lot of confusion later. This app is not:

✗ Not a database app

There is no database, no user accounts, and no login anywhere. The only data it stores is your theme preference in the visitor's own browser.

✗ Not a CMS

Content lives in two TypeScript files, not in an editor. Changing a case study means editing code and deploying. There is no dashboard.

✗ Not a checkout

No payments are taken. The calculator produces an estimate, not an invoice, and the page says so in small print under the result.

✗ Not a client portal

Every case study preview is either a public URL or a public YouTube video. Nothing private is exposed.

Every technical word this document uses, explained without jargon.

The people and the places

You / the owner
The person who owns this code and this business. Everything in this document is written for you.
Visitor
Anyone who opens the live site. They are never logged in, identified, or tracked.
Cloudflare
The company that actually serves the website to visitors and runs the code. Free at this scale, and it is what makes hosting cost nothing.
Cloudflare Worker
The always-on program that runs when somebody visits. It is the shopfront and the staff.
Resend
The service that actually delivers your email. Without it the contact form cannot send anything.
GitHub
Where the code is stored, with a full history of every change ever made.
Repository
The GitHub project folder. This document's portfolio-site repository is public, so anything committed to it is readable by the whole world.
The live site
The public address visitors see. It is built from your code, so the code and the live site are never quite the same thing until you deploy.

The parts of the code

Component
A reusable chunk of page. The navigation bar is a component. The whole page is assembled from six of them.
Page
One address on the website. This app has exactly one: the home page at /.
Server component
Code that runs on the server only and is never shipped to the visitor's browser. Used for the page skeleton because there is no reason to send unnecessary code.
Client component
Code that ships to the browser and can respond to clicks, typing, and scrolling. Five of the six sections are client components.
Route handler
A URL endpoint that receives data instead of returning a page. /api/contact is the only one, and it receives form submissions.
Props
Values handed down from a parent to a child component. The page hands the booking URL to two components this way.
State
A value that changes while the page is open. React re-draws the screen every time state changes.
TypeScript
JavaScript with a rulebook attached, so mistakes are caught before the code runs. Every .ts and .tsx file here is TypeScript.
JSX
The HTML-like syntax inside .tsx files. It looks like markup but it is really code.
Tailwind CSS
The styling system. Instead of writing a stylesheet, each element carries short class names that describe how it should look.
Icon library
A package of ready-made line icons used throughout the page, so no icon ever has to be drawn by hand.

Building and publishing

Build
Turning your source code into files a browser and a server can actually run. Nothing is live until this happens.
Deploy
Publishing a build to Cloudflare so the world can see it. A deploy is the moment a change goes live.
Prerender
Building the page into finished HTML before anyone asks for it. This page is prerendered, which is why it loads instantly.
Bundle
The collection of files produced by a build, ready to ship.
Commit
A saved snapshot of your changes in Git, with a message explaining what changed and why.
Push
Sending commits from your computer to GitHub. A push is what triggers the automatic build and deploy.
Rollback
Un-publishing a bad deploy and returning to the last version that worked.
node_modules
The installed third-party code. Never edit it, never commit it, and just delete the folder and reinstall if it breaks.
Package.json
The list of what is installed and the named commands you can run. The single most important file to read.

Configuration, secrets and data

Environment variable
A setting stored outside the code so it can differ per environment. The same code can use a test key locally and a real key in production.
Secret
An environment variable holding a password. It is write-only in the dashboard: Cloudflare can use it, and nobody — including you — can read it back.
Plain-text variable
A setting that is safe to read, like a website address. It is not a secret and can be stored in the code.
Build-time vs runtime
Build-time is read once while the site is being built and frozen into the output. Runtime is read while the site is running. This app uses one of each, and it matters a great deal — see section 20.
localStorage
Tiny storage inside the visitor's own browser. It never leaves their device and is cleared if they clear their browsing data.
Iframe
A window showing another website inside yours. This is how the case studies show the real, working apps.
Cookie
A small file a website stores in your browser. This site sets none.
LCP
"Largest Contentful Paint" — how long the main content takes to appear. The number that decides whether a visitor thinks your site is fast. Under 2.5 seconds is good.
FOUC
"Flash of Unstyled Content" — the ugly moment when a page briefly shows unstyled text before the styles arrive. This app avoids it.
Hydration
The moment an interactive page becomes clickable, after the browser loads and runs the code. Getting this wrong causes flickering and console errors.
Observability
Cloudflare's built-in logging. It is switched on, so you can see errors and traffic without adding any other tooling.
Monogram
The interlocking D and O symbol used as the logo. It is drawn from coordinates in code rather than being an image file, so it stays sharp at any size.

04 · The visitor's journey

What a visitor does, and what happens behind the screen at each moment.

Step 1 — The page arrives

The visitor types the address or follows a link. Cloudflare's edge network finds the machine closest to them and serves a finished HTML file. Nothing needs generating, so the page appears almost instantly. The dark theme is applied before the first pixel is drawn, so there is no white flash. Two web fonts are fetched from Google and the rest of the styling is a single small stylesheet.

The interactive parts of the page then load as a small bundle of JavaScript. Until that finishes, the page is readable but the typewriter headline and buttons are not yet animated.

Step 2 — First impression

The availability badge pulses. The headline types out web apps., pauses two seconds, backspaces, and types websites. — cycling through twelve specialities forever. Two buttons offer the next step: Calculate Project Scope (jumps to the calculator) and Book a Discovery Call (jumps to the contact section).

Step 3 — Proof

The visitor reaches the case studies. They can tap a category pill to filter, tap View Architecture to expand the problem / solution / result drawer, tap the external-link button to open the real live app in a new tab, or tap Live Preview to open the project inside a large modal with a fake browser frame — switchable between desktop and a phone-shaped frame. For the flagship video project, the modal shows a still image from YouTube and only loads the actual video if the visitor presses play.

Step 4 — Trust

The process section states how the work gets done in four steps with timings, followed by three written guarantees: full code ownership, weekly updates, and a thirty-day warranty.

Step 5 — Self-service pricing

This is the part visitors actually spend time on. They pick a project type, a stage, and any add-ons. A sticky summary card on the right updates instantly with a price range and a timeline, in whichever currency they selected. Nothing is pre-selected that they did not choose.

Step 6 — The hand-off

Two paths. The instant path: the visitor presses Lock In This Estimate & Book Call, the page writes their estimate straight into the contact form below, and scrolls them there. The deliberate path: they press Submit Project Inquiry, the page checks their details, sends them to the server, and the server emails you a formatted brief. Either way they can also skip everything and just message you on WhatsApp.

💡
The single most important behaviour

The bridge between the calculator and the form is what makes this site work. Without it the visitor would have to retype everything. With it, a visitor who spent two minutes pricing a project arrives at the form with the numbers already filled in, and all they have to do is add a sentence. It is the difference between a curious visitor and a lead. It is documented in full in section 13.

05 · How it is built

The four layers between a visitor and an inbox.

A modern website like this is really four programs stacked on top of each other. Each layer only ever talks to the one directly above and below it. Understanding which layer a change belongs in is most of what makes maintenance easy.

Layer 1 — The visitor's browser
The HTML, CSS and JavaScript that make up everything the visitor sees and clicks. The five interactive sections run here. This layer also holds the theme choice and the calculator state, and it is where the contact form is checked before anything is sent.
↓
Layer 2 — The Cloudflare Worker
The always-on server program, running in Cloudflare's network in hundreds of locations at once. It serves the page, and it runs the one API endpoint, /api/contact. It also holds the Resend key. This layer is what the OpenNext build tool produces and what wrangler deploy uploads.
↓
Layer 3 — The Next.js application
The framework that shapes everything: how pages are assembled from components, how the server program is generated, and how the contact endpoint is defined. Next.js is not doing anything clever here — it is the plumbing. OpenNext translates its output into something Cloudflare can run.
↓
Layer 4 — Resend, the outside world
The email company. It accepts the message, proves the Worker is allowed to send it using the API key, and delivers it to your inbox. If Resend is down or the key is wrong, the form fails — and the visitor is told to use WhatsApp instead.

The three build tools and what each one does

This is genuinely confusing the first time, so here is the plain version:

1️⃣ Next.js build

Produces a standard Next.js output folder. On its own this is not deployable to Cloudflare — it assumes a Node.js server.

2️⃣ OpenNext

Reads that output and rewrites it into a Cloudflare Worker plus a set of static assets. This is the translation step.

3️⃣ Wrangler

Uploads the Worker and the assets to Cloudflare and points the public address at them. This is the moment it goes live.

Running npm run deploy performs all three in order. Steps 2 and 3 are the ones that can fail for Cloudflare-specific reasons, and the failure messages are covered in section 27.

📌
This version of Next.js has breaking changes

The framework installed here is newer than most tutorials and guides describe. Before changing anything, read the guides bundled inside the installed package at node_modules/next/dist/docs/ — they are the authoritative reference for this exact version, and they may contradict what you have read elsewhere. AGENTS.md in the project root carries the same warning and is re-created automatically by the development server.

12 · The estimating formula

The exact arithmetic, worked through with real numbers.

The equations

🧮 How a price is calculated
// 1. Scale the base range by the stage
baseMin   = projectType.basePrice[currency].min   × stage.multiplier
baseMax   = projectType.basePrice[currency].max   × stage.multiplier

// 2. Add the cost of every selected add-on, once, to BOTH ends
addonsCost = Σ addon.price[currency]   for each selected add-on

// 3. Final range
finalMinPrice = round(baseMin + addonsCost)
finalMaxPrice = round(baseMax + addonsCost)

// 4. Timeline: the base weeks are scaled, then the add-on weeks are added
addonsExtraWeeks = Σ addon.extraWeeks   for each selected add-on
minWeeks = round(projectType.baseWeeks.min × stage.multiplier) + addonsExtraWeeks
maxWeeks = round(projectType.baseWeeks.max × stage.multiplier) + addonsExtraWeeks

Four consequences worth understanding, because they are deliberate:

  • The multiplier applies to the range, not to the total. Both the minimum and the maximum are scaled, so a production build is a genuinely bigger project, not the same project with tax added.
  • Add-ons lift, they do not widen. A ₦250,000 add-on adds ₦250,000 to both ends. The visitor pays a predictable extra, not a vague one.
  • Timeline uses the multiplier too — a production build takes half as long again, not the same time.
  • Only the timeline adds up; the price is a range. Two weeks per add-on, added to both ends, keeps the promise "this will not take twice as long".

  • Thousands are always separated with commas, in a consistent international format regardless of the visitor's device language. This is deliberate: a number that renders as "1200000" on one phone and "1,200,000" on another undermines trust in the whole figure.

13 · The estimator bridge

How the calculator fills in the contact form for you.

The two sections are siblings in the page — neither is inside the other, and neither imports the other. They talk through the browser itself. This is the most clever thing in the codebase and also the easiest to break by accident.

The mechanism, step by step

1️⃣
Visitor presses the button
"Lock In This Estimate & Book Call" in the summary card. Nothing is sent anywhere — this is entirely local to the page.
↓
2️⃣
A summary string is assembled
Five lines: the marker, the project, the stage, the price range with its currency, the timeline, and the chosen add-ons (or "None").
↓
3️⃣
A custom browser event is broadcast
Named populate-estimate, carrying the project name and the summary text. Any listener anywhere on the page can hear it.
↓
4️⃣

The form registered a listener when the page loaded. It sets the category dropdown and writes the summary into the message box, followed by a blank line and "Additional notes:" so the visitor can add their own words.
↓

The page scrolls down
Smoothly, to the contact section — so the visitor lands looking straight at the form they just filled in.

The category dropdown is also set to match the chosen project, so the email arrives with the right label without the visitor touching it. The message box uses a monospaced font precisely because the block above is a pre-formatted summary — a proportional font would wreck the alignment.

The three things that can break it

⚠ Renaming the event

If you rename populate-estimate in one file and not the other, the form silently stops being filled. The page still works; you just lose the hand-off. There is no error to chase.

⚠ Moving the sections

The scroll relies on an element with the id contact existing. Remove or rename that id and the button fills the form but no longer scrolls.

⚠ Changing the marker

The [ESTIMATE LOCK-IN] line is what you scan for in your inbox to spot a calculator lead. It is a plain string in the code, not a constant.

✓
Why this design is the right one

Neither component knows the other exists. The calculator does not import the form, and the form does not import the calculator. They agree on a single event name, exactly like two phone numbers agreeing on a ringtone. You can rebuild either section entirely without touching the other — which is a large part of why this project stayed easy to change.

Dark mode is the default and the design that was drawn first. Light mode is applied on top of it by a set of overrides, not designed from scratch. That is why light mode looks like "the same site, made readable" rather than a different product.

src/app/api/contact/route.ts builds an HTML email out of visitor input. Every interpolated value is now passed through escapeHtml(), and the two values used in mail headers through singleLine(). Keeping the internal documents out of search results

The eight working documents in public/ are not marketing pages. They stay open at their normal addresses so you can read them, but they must never appear in a search result. The two Android download pages are the exception: they are part of the public showcase, so they are indexable and are deliberately left out of the rules below. That is handled in public/_headers, which sends this on every one of them: 

X-Robots-Tag: noindex, nofollow, noarchive

Why a response header rather than a robots.txt rule. This is the part that surprises people. A Disallow in robots.txt does not stop a page from being indexed — it stops the crawler from fetching the page, which means it never gets far enough to read an instruction telling it not to index. Google documents the failure mode: a blocked URL can still appear in results as a bare link with no snippet, and it can only be removed via a manual request. X-Robots-Tag is delivered with the page, so the crawler reads it and honours it. That is the only mechanism that reliably keeps something out of results.

For the same reason there is deliberately no Disallow block for these paths in robots.txt. Adding one would undo the header. The two mechanisms conflict, and the header is the one that works.

⚠️
What this does and does not do

It does: remove these pages from search results, so nothing you wrote internally can surface through a search engine, and stop them being crawled at all.

It does not: stop a person who already has a URL. This is not authentication and it is not a login. Anyone who has bookmarked or been sent /app-documentation can still open it, exactly as intended.

If you ever need real access control — something secret, rather than merely unlisted — that requires authentication in front of the site, not a header.

Accessibility and performance

♿ Reduced motion is honoured

⚡ No new dependency

One thing worth knowing: working through all twelve services at the current speeds takes roughly 47 seconds before the first explosion. Shortening the list or the pause would bring it forward; nothing needs changing in the code to do that, only the DYNAMIC_SERVICES list in Hero.tsx and the pauseDuration prop.

🛡 On the server

  • A rejected bot is told it succeeded. The response is the same success shape a real submission gets. Telling a bot it was caught only teaches it what to change, and lying to software costs nothing. The server logs the rejection for the site owner.

Deploying without breaking the contact form

⚠
Always deploy with npm run deploy. Never npx wrangler deploy.

This is not a style preference, it is the thing that broke the form in production on 30 September 2026. The deploy script already passes --keep-vars to wrangler. Running wrangler directly omits that flag, and wrangler then drops bindings that are not declared in wrangler.jsonc — which is where every secret lives. The form started returning 500 with “Email delivery is not configured” while the code, the build, and every page on the site all looked perfect.

The reason this was so hard to see: the key is not inlined at build time. The built route reads process.env.RESEND_API_KEY at request time, so a local build that works locally proves nothing about production. And having a key in .dev.vars or .env.local is also no evidence — neither file is read by a deployed worker.

So there is now a command that asks the questions a build cannot. npm run preflight checks that RESEND_API_KEY is actually bound to the deployed worker using wrangler secret list, confirms the four public pages respond, and submits a real message through the live endpoint. The trap: build time versus runtime

This is the thing that causes the most confusion on this project, so here it is in plain language.

🏗 Build time (BOOKING_URL)

The correct way to undo something that is already in the history, because it leaves a permanent record of both the mistake and the fix.

10 Test the contact form's failure paths
No code change — this is a test you should run regularly.

11 Add a field to the contact form
Files: src/components/ContactHub.tsx, src/app/api/contact/route.ts, and src/app/privacy/page.tsx

Adding a field touches three files, and skipping the third one is the mistake that matters — a form that collects something the privacy policy does not mention is the exact problem that policy exists to prevent.

  1. Add it to the form state. In ContactHub.tsx, add the key to the formData initial object with an empty value, then add the input and bind it the same way the existing fields are bound.
  2. Escape it on the server. In src/app/api/contact/route.ts, create a matching safe… variable next to the existing ones:
    • lands in the HTML body → escapeHtml(value)
    • lands in the subject line → singleLine(value)
    • goes into a URL → encodeURIComponent(value)
    Then use the safe… name in the template, never the raw one. This is the step that closes the injection hole described in section 17; using the raw value puts it straight back.
  3. Add it to the email template, using the escaped variable.
  4. Add it to the policy. In src/app/privacy/page.tsx, add a row to section 02 “What we collect, and why” saying what the field is for. Then update the LAST_UPDATED date at the top of the file. If the field is optional, say so, and if it changes the retention period or adds a processor, sections 04 and 05 need updating too.
  5. Check the file map. Run npm run filemap:check. Nothing changes unless you added, renamed or removed a file — changing a field inside an existing file needs no edit here.
✓Then: run recipe 10, because a new field is also a new failure path.

27 · Problems already solved

Real failures from this project, what caused them, and how each was fixed.

Every entry here is something that genuinely went wrong during the build of this site. Keeping them written down is the reason a repeat of any of them would be recognised in seconds rather than hours.

The whole site failed to build, and the contact route returned an empty 500Fixed
Symptom
The build failed with no useful message, and any form submission returned a blank server error.
Cause
The email client was being constructed once when the module loaded, rather than per request. With no API key present, the constructor threw immediately — and because that happened while the module was being evaluated, it took the entire build down, not just the one endpoint.
Fix
Construct the client inside the request handler, after an explicit check for the key. A missing key now returns a clear 500 with a helpful message instead of crashing anything.
Prevention
Never let a constructor that can fail run at module scope. Check the thing it needs first, and return a helpful error.
A blank or broken page in the browser, with an error about a function not being definedFixed
Symptom
The page rendered but was not interactive, and the browser console reported that an internal helper function was not defined. Theme switching and animations failed.
Cause
The build tool's name-preservation helper was leaking into the small inline scripts that the theme library injects into the server-rendered HTML. Nothing in the browser defines that helper, so every inline script threw on arrival.
Fix
Set keep_names to false in wrangler.jsonc. This requires Wrangler 4.13.0 or newer — the version in this project is far beyond that.
Prevention
The setting and its explanation are written as a large comment directly above it, so nobody strips it out while tidying the file.
Deployment failed with an error that a Worker "was not found"Fixed
Symptom
Deploying failed with a specific error code complaining that a referenced Worker could not be found.
Cause
The Worker's own name and the name inside its self-reference binding had drifted apart. The framework's routing references the Worker by name, so the two must be identical.
Fix
Set both to the same value. The exact error message and the requirement are now written as a comment at the top of wrangler.jsonc, including the error code, so the next occurrence is instantly recognisable.
The "Book a Call" button led nowhereFixed
Symptom
There was a call-to-action button that went to a placeholder, and a contact card promising a booking with nothing to book.
Cause
The booking page had not been created, but the button was already on the page pointing at nothing.
Fix
Two changes. First, a real booking address is read on the server and passed down to both components, so it can be changed in one place. Second — and this is the durable part — when no address is configured, the button falls back to the contact section and the card falls back to WhatsApp, and the labels change to match. The button can no longer be a dead link.
Note
Because the home page is prerendered, this address is read at build time. Changing it needs a new build. See section 20.
The YouTube preview in the project modal was permanently blankFixed
Symptom
Opening the flagship project's preview showed an empty box with a small unreadable error in the corner.
Cause
YouTube's normal watch page deliberately refuses to be embedded — it sends a header telling browsers not to frame it. The data file had been storing a full share link, which resolves to exactly that watch page. Only YouTube's dedicated embed address is designed to be framed.
Fix
Two changes. The data file now stores only the bare video ID, with the thumbnail and embed addresses built from it in the component — so there is no URL format left to get wrong. And the embed now uses YouTube's privacy-enhanced host rather than the standard one.
Prevention
The reasoning is written directly above the field in the data file, including why a share link must never be used.
The page was loading YouTube's player before anyone wanted to watch a videoFixed
Symptom
Opening the video preview immediately downloaded around a megabyte of player code and fired tracking requests, even for visitors who never pressed play. It also meant the video could become a cookie-consent trigger.
Cause
The player was created as soon as the modal opened.
Fix
Added a facade: a still image from YouTube's image service with a play button on top, and the real player is only created on click. The image is not a page-level image, so it does not affect loading speed at all.
Also
High-resolution thumbnails do not exist for every upload, so the facade tries progressively smaller sizes and steps down automatically if one fails to load.
The calculator showed a price higher than the visitor had actually chosenFixed
Symptom
The estimate included the cost of an add-on before the visitor had selected anything.
Cause
One of the add-ons was selected in the component's starting state.
Fix
Nothing is selected on load. The total now reflects only deliberate choices, which is both more honest and a better first impression — a visitor who sees their own number immediately is far more likely to fill in the form.
Note
The project type and stage still start selected, because a price must always be visible. The comment explaining this is in the code.
The headline briefly showed nothing after "I build high-impact"Fixed
Symptom
On a first visit, a new visitor saw the fixed half of the headline with an empty gap beside it for a moment before the first word began typing.
Cause
The animated text started as an empty string. Because that initial value is also used on the server, the fix had to work for both the server-rendered HTML and the browser.
Fix
The first phrase is now the starting value, so the very first paint already contains a word and the animation continues from there. This also keeps the server and browser output identical, which is what prevents a mismatch.
The theme toggle flickered and the page flashed white before turning darkFixed
Symptom
On load, the theme button briefly showed the wrong icon, and the page flashed light before settling into the dark theme.
Cause
Two separate issues. The icon is drawn from the current theme, which the server cannot know — so the server and the browser produced different output. And the theme was applied after the first paint instead of before it.
Fix
Two fixes. The button now draws an empty placeholder of exactly the same size until the page has loaded, so server and browser always agree. And the stored theme is applied before the first paint, so a returning visitor's page opens in their chosen theme with no flash.
Note
The button deliberately ignores the operating system setting and defaults to dark, because dark is the design that was drawn first.
Every piece of text on the site looked small, especially on phonesFixed
Symptom
The site was technically correct but felt cramped and slightly illegible on a phone, despite every text size being individually adjusted.
Cause
Sizes were being managed one element at a time, which is both laborious and inconsistent.
Fix
The root font size was raised from 16 to 18 pixels. Because every size utility is relative to that root, the entire site enlarged by 12.5% from a single line. That one line is now the documented lever for site-wide text size.
A live API key was written into a file that is published to a public repositoryResolved
Symptom
A working email API key was pasted into the Cloudflare configuration file while trying to make the form work locally.
Why it matters
That file is committed, and the repository is public. Anything written into it is readable by anyone on the internet, permanently, in the history even after a later commit removes it.
Resolution
The change was reverted before it was ever committed or pushed, and the key was confirmed absent from the published history. Local development uses a settings file that is already excluded from Git, and production uses the dashboard's encrypted secret store.
Standing rule
Never put a key in wrangler.jsonc. Deploy commands already pass a flag that preserves dashboard secrets, so there is never a reason to. This incident is why the deploy and upload commands carry that flag.

30 · The housekeeping rule

The one rule that keeps this project from rotting — and the list of things still to finish.

★ The rule
  1. Every change updates the documentation in the same commit. If you change how the app behaves, this document changes with it. If you change how it looks, the Brand Guidelines change with it. If you change how it is set up, the README changes with it.
  2. The README stays short and non-sensitive. It is the first thing a visitor, a client or a potential collaborator reads. It holds a summary, the setup steps, and links — never a key, a token, or a private detail.
  3. This document holds everything else. The detail, the reasoning, the failure modes and the history. Nothing in it is a secret either: variable names, purposes, storage locations and failure behaviour belong here; the values of credentials never do.

The LinkItem type, in full

links is the only field that holds objects rather than a plain value. It is defined in the same file as ProjectItem, above it:

PropertyRequiredWhat it is
titleYesShort, human label for the link. A few words. Rendered in the emphasis weight above the subtext, at text-sm — 15.75px, because the root type size is 18px.
subtextYesOne sentence in smaller type explaining where the link goes and what it does. This is the reason the link exists — without it the visitor has to open the link to find out what it is. Rendered at text-[13px].
hrefYesThe absolute URL including the https:// scheme. Opened in a new tab with rel="noopener noreferrer". Not validated — a relative or malformed URL will simply fail when clicked, so check them.

The whole block is optional, and a project with no supplementary links renders exactly as it did before. Two of the five case studies currently use it: the factory ERP links to its demo recording, and the Bible reading plans link to the two sibling plans that live on the same address.

Do not duplicate what already has a button. The GitHub and live-site icons on each card are driven by githubUrl and liveUrl. Use links for things neither of those covers — a write-up, a demo recording, a documentation page, a related project. Putting a live-site link in both places gives the same destination two competing treatments and the visitor no reason to prefer one.

⚠️ Two things that caught this out, and will catch the next thing

1. Arbitrary pixel sizes do not scale with the type system. The site sets html { font-size: 18px }, so rem-based utilities resolve larger than their Tailwind names suggest — text-xs is 13.5px and text-sm is 15.75px. But text-[11px] is a flat 11px regardless. The subtext was authored against a 16px assumption and came out as the smallest text on the entire card, smaller than the tech tags beside it. When using text-[Npx], calculate from 18px, not 16px.

2. A colour not in the light-mode override list is invisible in light mode. The engine in globals.css remaps a specific list of text classes — currently text-white, text-slate-300, text-slate-400, text-slate-500, text-emerald-300 and text-emerald-400. The title was written as text-slate-200, which is not in that list, so on a light canvas it rendered at roughly 1.1:1 contrast and could not be read at all. Restrict new text colours to the six listed above, or add the class to globals.css in the same change.
