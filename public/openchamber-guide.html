OpenChamber, on your phone

OpenChamber is a graphical front end for OpenCode — the AI coding agent — and it can run in a browser, which means it can run on a phone. This document covers the whole thing: installing it, the three different ways to reach it from a phone, the security decisions that actually matter, every command, and what to do when it breaks.

37 sections 8 parts ~40 min read MIT licensed 10.9k GitHub stars Internal document
📱
If you only want the short version

Install OpenCode, install the OpenChamber CLI, run openchamber --ui-password something-strong, open the URL it prints, and press Install in your phone's address bar. That is a working OpenChamber on that phone, on your home Wi-Fi, today.

To reach it away from home there are two genuinely different options and they are not equally safe. 17 · Which one you should pick explains the difference, and it is the most important decision in this document.

🔐
Read this before you do anything else

OpenChamber gives whoever reaches it access to your machine and your code, and it can run terminal commands. It listens on your own machine only by default, which is the right default. The moment you expose it to the internet, you have published a control panel for your own computer. Read 18 before you expose it, and set a strong password every single time.

I What it is

01 · Why this document exists

Because the instructions are scattered across a large site and the security bits are easy to miss.

OpenChamber is a genuinely useful tool, and its documentation is good — but it is spread across a large documentation site, a GitHub README, and several pages that each assume you already know terms from the others. The pages that matter most for using it from a phone are not the ones a search engine hands you first.

This document puts it in one place, in the order you actually need it, and spends as much time on the security decisions as on the installation. It is written to be read once and referred back to.

It is an internal working document, not a client-facing one. It is excluded from search results, so nothing here will ever be indexed.

02 · What OpenChamber is

A graphical interface for an AI coding agent. That is the whole idea.

OpenCode is a command-line AI coding agent. You give it a task, it reads and edits your code, runs commands, and reports back. It is powerful, and it is entirely text-based.

OpenChamber is the interface around that. It shows you the conversation, the files that changed, the diffs, the terminal, running processes and their output — as a proper application rather than a wall of text in a terminal. It is the difference between driving with a command line and driving with a dashboard.

It ships in four forms, and they are the same product: a desktop application, a web application you can install like a phone app, a VS Code extension, and native iOS and Android apps. At the time of writing it had roughly 10,900 GitHub stars, more than 4,000 commits, and an MIT licence, so it is open source and actively developed.

The one-sentence version: OpenChamber lets you supervise an AI coding agent from a browser — including the browser on your phone — without sitting at your desk.

03 · How it relates to OpenCode

OpenCode does the work. OpenChamber is the way you watch it happen.

The relationship matters because it explains the setup order. OpenChamber does not replace OpenCode and it does not contain it. It runs on top of an OpenCode server, which it will start for you if one is not already running.

There are three arrangements, and they matter at different times:

ArrangementWhat happensWhen to use it
Managed OpenChamber starts and manages its own OpenCode server for you The default. Simplest, and correct for almost everyone.
Attach You already have an OpenCode server, so OpenChamber connects to it You run OpenCode in a terminal or a service already, or you want the sessions shared
API only OpenChamber serves API routes but no browser interface Headless servers where only the desktop or mobile apps will connect

OpenChamber is an independent project and is not affiliated with the OpenCode team. It was chosen because OpenCode is open source, has a solid API, and is easy to extend. It is a third party relying on another project, which is worth remembering when you are deciding how much to trust it with your machine.

04 · The four surfaces

The same product in four shapes. You probably only need two.

SurfaceBest forNotes
Desktop app Day-to-day work on macOS, Windows or Linux The complete workspace. Multiple windows, remote machines, SSH, native notifications. Bundles its own OpenCode, so no separate install is needed.
Web / PWA Remote access, and working from a phone Hosted by the CLI, installable as an app. This is the one this document is mostly about.
VS Code extension Sessions beside your code Send selections to the agent, open results in the editor, compare parallel runs.
iOS / Android Reviewing and steering work away from your desk iPhone is on TestFlight. Android is an APK from the releases page. Uses the encrypted relay, so it works from anywhere with no public URL.

The project's own guidance is: desktop for day-to-day work, web for remote access and reviewing from your phone, VS Code for sessions right next to your code.

05 · What you can actually do with it

A realistic list, not the marketing version.

  • Chat with your agent and see what it changed as a proper diff, file by file, instead of a wall of text.
  • Run a terminal inside it, with the output rendered properly.
  • Start and watch dev servers, and preview the result in a panel beside the conversation. On the desktop app you can point at an element on a page and send the agent that element's screenshot, styles, position and browser errors — which is a genuinely useful way to say "this thing here".
  • Set a goal for a session and let it keep working until it is met, blocked, or hits a limit you set — and let it keep going after you close the app.
  • Run the same task on up to five models at once, each in its own session and optionally its own worktree, then compare what each actually built and keep the best, or fuse the strongest parts together.
  • Turn a large diff into a guided walkthrough that groups related edits into steps in the order that makes sense.
  • Work from a GitHub issue or pull request, with context attached, and send failed checks back to the agent.
  • Schedule recurring work — once, daily, weekly, or on a cron schedule.
  • See everything at a glance: which sessions are working, waiting, finished or failed, plus approvals, token use and cost.
  • Keep notes, todos and reusable project actions next to the sessions they belong to.

For a phone specifically, the useful set is narrower: watch progress, answer questions, review diffs, and steer. 29 is honest about what does not work well on a small screen.

06 · The honest caveats

Things to know before you commit to it.

  • It is a fast-moving third-party project. At the time of writing it was around version 1.23, which the documentation references when describing a data-directory migration. Expect the interface and the commands to change, and expect occasional breakage.
  • It is young. Thousands of stars and an active community, but also hundreds of open issues and a large number of pull requests. That is normal for a popular project, and it is not the same as stability.
  • Two projects, one supply chain. It sits on top of OpenCode. A problem in either reaches you.
  • The install script is a pipe from the internet into your shell. It is the documented method and the project is reputable, but you should still look at what you are running.
  • It runs commands as you. Whatever the agent does, it does with your permissions. That is the point of an agentic tool and also its risk.
🔎 A note on one documentation inconsistency

Some third-party write-ups and older copies of the package README show the install command pointing at a btriapitsyn/openchamber repository. The current official documentation, and the current README on the project’s own repository, both use openchamber/openchamber. Use the official one, and if you ever see the other in an install command, stop and check.

II Installing

07 · Before you start

What you need, and what to check first.

If you already have OpenCode running well, you are ready. If you do not, install that first — the next section covers it.

08 · Install OpenCode

The prerequisite, briefly.

OpenCode installs with a one-line script on macOS and Linux:

curl -fsSL https://opencode.ai/install | bash

On Windows, follow the official instructions for OpenCode, which account for the differences in how the shell works there. If you use the desktop app of OpenChamber you can skip all of this — it bundles its own copy.

Confirm it works before moving on. Run opencode --version. If that fails, OpenChamber will not start correctly, and the error it produces will point at OpenChamber rather than the real cause.

The general principle: before piping anything from the internet into a shell, it is worth thirty seconds to read it. curl -fsSL URL fetches silently, so -fsSL on its own shows you nothing.

09 · Install the web version

The one you want for phone access.

The documented install is a single line:

curl -fsSL https://raw.githubusercontent.com/openchamber/openchamber/main/scripts/install.sh | bash

Note the repository in that URL: openchamber/openchamber, the official one.

If you would rather see what you are running, download the script first, read it, and then run it: 

curl -fsSLO https://raw.githubusercontent.com/openchamber/openchamber/main/scripts/install.sh
less install.sh
bash install.sh

The package can also be installed directly through a package manager, which is the better habit if you have one: 

bun add -g @openchamber/web
# or
npm install -g @openchamber/web
# pnpm add -g @openchamber/web
# yarn global add @openchamber/web

Once installed, start it with a password. The password is not optional if you intend to reach it from anywhere: 

openchamber --ui-password be-creative-here

The CLI prints the URL it is serving on, usually http://localhost:3000. Open that and you should see your session list. That is a working installation.

Generate a real password, not the example. The project's own docs use be-creative-here as a placeholder, which is fine in a tutorial and catastrophic in practice. Use your password manager. A long passphrase is both stronger and easier to type on a phone than a short complex one.

10 · Install the desktop app

The complete workspace, and the easiest path to a first success.

Download the latest build from the GitHub releases page. It is available for macOS, Windows and Linux, and it bundles the matching OpenCode CLI, so no separate OpenCode install is needed.

On Linux the release is an AppImage:

chmod +x OpenChamber-*.AppImage
./OpenChamber-*.AppImage

Keep the AppImage in a writable location, or in-app updates will fail. AppImages need FUSE (libfuse.so.2). Without it, run with APPIMAGE_EXTRACT_AND_RUN=1.

11 · Install the VS Code extension

Thirty seconds, if you use VS Code.

Install OpenChamber from the Visual Studio Marketplace, or search for "OpenChamber" in the Extensions view. It opens in the sidebar. The extension uses your installed OpenCode CLI, so it needs the same prerequisites as the web version.

12 · Your first run

A ten-minute sanity check before you rely on it.

  1. Start OpenChamber with a password and open the printed URL.
  2. Confirm the session list loads. An empty list is correct — you have no sessions yet.
  3. Check the server status. On the homepage there is a See Servers control that shows connected servers and whether OpenCode is running.
  4. Start one small, harmless session. Ask it to read a single file and tell you what is in it. It can read but not change anything, so there is no risk.
  5. Confirm you can see the result and that the session appears in the list.
  6. Only then consider exposing it to a phone or the internet.

If something is wrong at this stage, fix it before adding remote access — a connection problem and a configuration problem look identical once you are debugging from a phone.

III Your phone

This is the part people actually want, and it is where the security decisions live. Read 18 before you expose anything.

13 · Three ways to reach it from a phone

They are genuinely different, and the difference is security, not convenience.

ApproachWorks away from home?Public URL?Risk
A · Home network only No No Low
B · Pairing + Private Relay Yes No Lowest
C · Public tunnel to the browser Yes Yes Higher

The key fact, straight from the documentation: for your own devices, you usually do not need a tunnel. Pair them and the end-to-end encrypted Private Relay handles away-from-home access with nothing publicly exposed at all.

ℹ️ The one place a tunnel is genuinely required

You asked about reaching it through a phone browser. That is the PWA, and the PWA cannot use the relay — the relay works with the native mobile apps. The documentation says so directly: “To reach the PWA from outside your network you’ll need a tunnel and a strong UI password — the native apps handle this for you via the relay.”

So for away-from-home phone use, the honest advice is: install the native app and pair it. If you specifically want the browser, you need a tunnel, and that is a materially larger risk. Both routes are documented below.

14 · Option A: home network only

The simplest thing, and it is enough for most people.

If you only ever want OpenChamber on your phone while you are at home, you need no tunneling, no relay, and no public address. Both devices just need to be on the same network, and the server needs to be willing to listen on it.

Step 1 — let the server listen on your network

By default OpenChamber binds to 127.0.0.1, which is that machine only. To reach it from your phone you must deliberately widen that: 

openchamber --lan --ui-password be-creative-here

Always combine --lan with a strong password. Those are not two separate decisions — --lan on its own is an open door on your home network, and every device on it, including anything compromised, can reach it.

Step 2 — find the address

Ask the CLI:

openchamber connect-url --port 3000 --qr

This prints a link and a QR code. Scan it with your phone and you are connected. The command warns you with [LAN_UNREACHABLE] if the direct route will not work — if you see that, your server is not actually listening on the network.

Step 3 — install it as an app

See 27. The main benefit on a home network is a full-screen app icon and no address bar.

⚠️ The limitation to understand

This works on your Wi-Fi and nowhere else. The moment you leave home — mobile data, a café, an office — it stops working, and the natural but wrong response is to reach for a tunnel. If you expect to use it away from home, go straight to 15 and do it properly.

15 · Option B: pairing and the Private Relay

The recommended way to reach your own devices from anywhere. Nothing is exposed publicly.

The Private Relay is OpenChamber’s answer to the problem that makes tunnels uncomfortable. Your server opens an outbound connection to relay infrastructure and keeps it alive. When your device is away from home it connects to the relay too, and the relay passes encrypted traffic between the two.

The critical property: nothing on your machine ever listens for incoming connections from the internet. The relay is a blind courier, not a middleman.

How it works, precisely

  • End-to-end encrypted. Your device and your server agree encryption keys directly with each other. The relay forwards sealed traffic it has no keys for. It cannot read your code, your prompts, or your passwords.
  • Only your devices can connect. A device must hold a token issued by your server through one-time pairing. Nobody can discover your server through the relay, and you can revoke any token at any time.
  • Pairing links are single-use. A QR code works exactly once and expires if unused, so a leaked old link is worthless.
  • It prefers a direct route. When you are home on the same Wi-Fi, devices connect directly and skip the relay entirely.
  • It manages its own lifecycle. It starts on demand when you create an Anywhere pairing, and shuts down automatically once no paired device relies on it.

Pairing, step by step

  1. On the computer running OpenChamber, open Settings → Remote Instances → Connect to this server and press Add a device.
  2. Give the device a name you will recognise later — My iPhone.
  3. Choose where you will use it:
    • This computer only — for apps on that same machine.
    • Home network only — direct over Wi-Fi, does not work away from home.
    • Anywhere — home and away, with away traffic through the Private Relay. This is the one you want.
  4. Press Create QR code.
  5. On the phone, open the native app and tap Scan QR code. Point the camera at it.
  6. The dialog closes on its own once the device connects, and the device appears in the list with a live status.

From a terminal instead

If the server runs headless, create the link from the command line:

# same network only
openchamber connect-url --port 3000 --qr

# works from anywhere — the equivalent of picking "Anywhere"
openchamber connect-url --relay --qr

A --relay link carries both routes: direct when it can reach the server, relay when it cannot. The relay starts on its own — a running instance picks it up within a minute, a stopped one on its next launch.

Managing paired devices

Settings → Remote Instances → Connect to this server lists every device that can reach the server, with a green dot when it is online and whether it is connected over the local network or the relay. Revoke cuts a device off immediately. Clear revoked tidies the list. The same physical device keeps one entry even if it signs in again later.

You can see live relay state — Connected, Reconnecting, and how many devices are using it — under Settings → Remote Instances → OpenChamber Relay. There is a Disable button there that cuts relay access off immediately, without affecting devices on your local network.

Installing the native apps

PlatformHow
iPhone / iPadJoin the TestFlight beta, then install the build
AndroidDownload the APK from the latest release. You will need to allow installation from that source.

You can pair the app with several servers and switch between them, and the app shows for each whether it is reachable and whether you are connected over the local network or the relay.

16 · Option C: a public tunnel for the browser

This is how you get OpenChamber in an ordinary phone browser from anywhere. It is also the option with the most risk.

A tunnel creates a public URL that forwards to your machine. Anyone with that URL can reach OpenChamber. This is what you need for the browser-based PWA away from home, and it is not what you want if pairing will do.

Step 1 — install a tunnel provider

OpenChamber starts the provider’s CLI on your machine, so install it first:

brew install cloudflared
# or
brew install ngrok

Cloudflare quick tunnels can run with cloudflared alone. Ngrok needs an account and an authtoken: 

ngrok config add-authtoken <your-ngrok-token>

Step 2 — start OpenChamber with a password

openchamber --ui-password a-long-passphrase-you-generated

You can skip this and let openchamber tunnel start auto-start a server, but being explicit means you cannot forget the password. Server options such as --port, --host, --lan, --ui-password and --api-only can be passed to the auto-start.

Step 3 — start the tunnel

# Cloudflare
openchamber tunnel start --provider cloudflare --mode quick --qr

# or Ngrok
openchamber tunnel start --provider ngrok --mode quick --qr

By default OpenChamber prints a QR code in interactive terminal sessions. Use --qr to force it, --no-qr to suppress it.

Step 4 — check it is up

openchamber tunnel status

When the tunnel is up, status shows the public URL. Open it, or scan the QR code, and OpenChamber is reachable from anywhere. On a phone, use the browser’s install option (27) to make it an app.

Modes and profiles

--mode quick is a throwaway URL. If you want a stable address, the managed modes use your own Cloudflare token and hostname: 

# managed remote — a token and hostname you control
openchamber tunnel start --provider cloudflare --mode managed-remote \
  --token-file ~/.secrets/cf-token --hostname app.example.com

# managed local — a local cloudflared config
openchamber tunnel start --provider cloudflare --mode managed-local \
  --config ~/.cloudflared/config.yml

# save it as a reusable profile
openchamber tunnel profile add --provider cloudflare --mode managed-remote \
  --name prod-main --hostname app.example.com --token-file ~/.secrets/cf-token

openchamber tunnel start --profile prod-main

Useful tunnel commands

openchamber tunnel providers
openchamber tunnel ready --provider cloudflare
openchamber tunnel ready --provider ngrok
openchamber tunnel doctor --provider cloudflare
openchamber tunnel doctor --provider ngrok
openchamber tunnel stop --port 3000
openchamber tunnel status --all

Behaviour worth knowing

  • One active tunnel per OpenChamber instance, keyed by port.
  • Starting a new mode or provider on the same instance replaces the previous tunnel.
  • Generating a new connect link revokes the previous unused one.
  • Tunnel auto-start preserves server flags such as --ui-password and --api-only across restart and update flows — which is a genuine convenience and also a reason to double-check the password is actually set.
🔐 What a tunnel provider can see

This is the trade you are making, stated plainly by the project's own documentation: “A tunnel provider decrypts traffic at its edge and sees every request in plain text.”

A tunnel provider can therefore see your prompts, your code, and anything you type into it. The relay exists precisely to avoid this. If you only need your own devices to reach your own machine, use 15 and skip this trade entirely.

17 · Which one you should pick

A direct recommendation.

You want to…UseBecause
Use it at home only, on your phoneA — home networkNo public exposure, no relay, no tunnel. Nothing to secure beyond the password.
Check on work from anywhere, and do not mind installing an appB — pairingEnd-to-end encrypted, no public URL, revocable per device. The recommended route.
Use it from any browser on any device, including a borrowed oneC — tunnelThe only option that gives you a plain public URL. Necessary here, and the reason it carries real risk.
Share access with another personC — tunnelRequires a URL they can open. Give them a separate strong password, and revoke it when you are done.
Run a server with no UI, and connect only from the desktop or mobile appB — pairing, API only--api-only serves the API without the browser UI, so there is no web surface to attack.
✅ My recommendation for you specifically

You asked about a phone browser, so tunnel C is what you asked for, and it will work. But the sequence I would actually follow is this:

  1. Start with A — --lan on your home Wi-Fi. Costs nothing, exposes nothing, and proves the whole thing works.
  2. Install the native app and pair it (B) if you want to check on work from anywhere. This is the safe version and needs no public URL.
  3. Add C only if you need a browser on an unpaired device. When you do, set a long passphrase, keep the tunnel off when you are not using it, and stop the tunnel when you finish.

That order is not timidity. It means the dangerous capability is the last thing you turn on, not the first, and you only enable it if you genuinely need it.

IV Security

18 · The threat model, plainly

Understand what you are protecting before you expose anything.

OpenChamber is not a website. It is a remote control for your computer, with the ability to run commands as you, read and modify your files, and drive an agent that can do all of that on its own. In the hands of an attacker it is a complete compromise of the machine it runs on.

So the only questions that matter are:

  1. Who can reach it? By default, only programs on your own machine. Widening that is always a deliberate act.
  2. How do they prove they are you? A password, a passkey, or a per-device pairing token.
  3. Can anyone else find it? With a tunnel, yes — anyone with the URL can try the door. That is why the password is not optional.
  4. Can a third party read the traffic? With a relay, no — it is end-to-end encrypted. With a tunnel, yes — the provider decrypts at its edge.

If you can answer all four correctly you are in good shape. Notice that nothing on that list is about encryption strength or a clever feature — it is entirely about reachability and authentication, which is where self-hosted tools are actually won and lost.

19 · Passwords, passkeys and device tokens

Three different mechanisms for three different situations.

The UI password

This protects the browser interface. Set it with the flag:

openchamber --ui-password your-password

Or, better, with an environment variable so it never appears in shell history:

export OPENCHAMBER_UI_PASSWORD='your-password'

After signing in, OpenChamber remembers the device for a while, so you are not prompted every time. That is a convenience, not a weakness — but it does mean an unlocked device on a shared machine stays unlocked for a while.

Always set a password if the instance is reachable by anyone else — especially over a tunnel or the public internet. It is the only thing standing between an open URL and your filesystem.

Passkeys

Once a password is set, add passkeys for much stronger, faster sign-in: Face ID, Touch ID, or a hardware security key. Add them at Settings → OpenChamber → Passkeys.

Passkeys are tied to the current password. If you change or remove the password, saved passkeys are cleared and you add them again. This is worth knowing before you rotate a password, or you will find yourself locked out of a fast sign-in you thought you had.

Device tokens

Devices paired through Connect a Device authenticate with their own per-device tokens, not the UI password. Pairing links are single-use and expire if unused. Every paired device is listed at Settings → Remote Instances → Connect to this server, where you can revoke any of them at any time. Away-from-home connections go through the Private Relay, which is end-to-end encrypted and cannot read your traffic.

The property that makes this safe: scanning a pairing code never exposes your UI password, and one device’s token cannot be used to impersonate another. So you can pair freely without weakening the password that protects browser access.

The honest comparison, in one table.

That is the whole case for the relay. The one thing the tunnel genuinely buys you is a URL that works in any browser on any device, with no app installed — which is exactly what you asked for, and also the only thing you give up privacy for.

21 · The rules I would follow

A short, opinionated list.

  1. Never expose it without a strong password. A long passphrase, from your password manager, unique to this. Not the tutorial's example.
  2. Put the password in an environment variable (OPENCHAMBER_UI_PASSWORD), not on the command line, so it does not sit in your shell history or in a screenshot of your terminal.
  3. Prefer pairing over tunnels for anything that is your own device. Reach for a tunnel only when you need a URL in an ordinary browser.
  4. Stop the tunnel when you are not using it. There is no reason to leave a control panel for your machine reachable from the internet overnight because you were using it at lunch.
  5. Use --api-only on headless servers so there is no browser UI exposed at all. Desktop and mobile apps still connect.
  6. Revoke devices you no longer use. The paired-device list is one click and takes seconds.
  7. Do not port-forward. Opening a port straight to your machine bypasses everything above. Use a tunnel or a VPN.
  8. Behind your own server, use HTTPS. The connection to a LAN or reverse-proxy setup is plain HTTP, so on a shared network anyone can read it. If others can reach it, put your own HTTPS server in front — see the project's reverse proxy guide.
  9. Update it. openchamber update. It is a tool with real privileges and it is moving fast.
  10. Never install extensions from a source you do not trust. An extension can send data off your machine. In enterprise mode, extensions that talk to outside addresses only install from repositories you list in allowedExtensions.
That last point is worth expanding for a solo user. OpenChamber has an extension system, and extensions can talk to external APIs, load from outside addresses, or run a background service. Installing one is closer to running third-party code on your machine than installing a browser extension is. Treat the extension list with the same suspicion as a package you would install from npm.

22 · Verify before you trust it

A five-minute security check worth doing once.

  1. Confirm the default is safe. Start OpenChamber with no flags and check what it listens on. It should be 127.0.0.1 — your machine only. If it is listening more widely than you expected, stop and find out why.
  2. Confirm the password is actually set. Open the UI without signing in. If it lets you straight in, there is no password and you must not expose it.
  3. Confirm the tunnel is not left running. openchamber tunnel status --all when you are not using it. If a tunnel is up that you did not start, stop it.
  4. Review paired devices. Anything you do not recognise, revoke. It takes one click.
  5. Test that the password is the only way in. With a tunnel up, try the URL in a private window with no cookies. You should get a login prompt.
  6. Add a passkey once you are confident, so the password is not typed into a phone keyboard every time.

V The command line

23 · Every command

The complete surface, so you can stop guessing.

Running it

openchamber                                # start on port 3000
openchamber --port 8080                    # custom port
openchamber --lan                          # listen on the network (0.0.0.0)
openchamber --lan --port 3000              # both
openchamber --ui-password secret           # password-protect the UI
openchamber --api-only                     # API routes, no browser UI
openchamber --host 0.0.0.0                 # explicit bind address
openchamber update                         # update to latest

--host 0.0.0.0 is required to listen on all interfaces, since the default is 127.0.0.1. Use --host <ip> or OPENCHAMBER_HOST=<ip> to bind to one specific interface instead.

Everyday operations

openchamber status                         # is it running?
openchamber logs                           # recent output
openchamber stop                           # stop it
openchamber connect-url --qr               # pairing link for this network
openchamber connect-url --relay --qr       # pairing link that works anywhere
openchamber startup enable                 # start at login as a service
openchamber update                         # update to latest

Headless and server use

openchamber connect-url --port 3000 --api-only --lan \
  --server http://workstation.local:3000 --qr --ui-password your-password

This runs OpenChamber as a web/API server on a remote machine so you can connect from OpenChamber Desktop on another machine. --api-only starts the API routes without serving browser UI assets.

⚠️ Client tokens are not UI passwords

The documentation is explicit: “Generating a client token does not automatically password-protect the hosted browser UI.” --ui-password protects browser access; a client token only lets another OpenChamber app connect. If you serve this on a network, you need both, and you need them to be different.

25 · Run it at login

For a machine that is always on.

If you want it available without launching it each time, enable the startup service. On Linux that is a systemd user unit: 

systemctl --user daemon-reload
systemctl --user enable --now opencode openchamber

The service file shown in the documentation is a minimal [Unit] WantedBy=default.target unit, enabled with systemctl --user enable. If you are running it as a persistent service rather than a desktop session, set OPENCODE_JWT_SECRET to a long random value so authentication tokens remain valid across restarts.

🔁 Remember this

openchamber startup enable snapshots your environment. Set your password and any other variables first, then enable the service. Otherwise you will end up with a service that is listening on the network with no password.

26 · Attach to an existing server

When you already run OpenCode yourself.

# attach to an OpenCode server on port 4096
OPENCODE_PORT=4096 OPENCODE_SKIP_START=true openchamber

# attach to a remote OpenCode server
OPENCODE_HOST=https://myhost:4096 OPENCODE_SKIP_START=true openchamber

OPENCODE_SKIP_START=true is what stops OpenChamber launching a second OpenCode server of its own. OPENCODE_HOST takes precedence over OPENCODE_PORT, and it must be an origin with an explicit port and no path, query, or hash.

Attaching is the right choice when you want the same sessions visible in your terminal and in the UI. There is also a related piece of OpenCode functionality worth knowing: you can attach a terminal TUI to a running web server, so both interfaces share the same sessions and state — opencode attach http://localhost:4096.

VI Using it well

27 · Installing as an app on each device

The PWA route, per platform.

A Progressive Web App is a web page that installs like a normal app: its own icon, its own window, no address bar. It is the browser-based option and it is what you use when you do not want an app store at all.

DeviceHow to install
Desktop browserUse the Install option in the address bar
iPhone / iPad (Safari)Share → Add to Home Screen
Android (Chrome)Menu → Install app / Add to Home Screen

Do this before trying to use it from a phone, not after. It makes the thing you tap look and behave like an app, and — more practically — it means a PWA you have already installed is far easier to reach when you are standing somewhere with a poor connection.

Once installed, a PWA is cached by the browser. It will still need a network round trip to reach your server, but it will open instantly and feel local rather than like a page being downloaded.

28 · Notifications

Knowing an agent finished while you are doing something else.

OpenChamber sends background notifications so you know when the agent has responded, even from another tab or another device. This is the single most useful feature on a phone, because the usual problem is not the interface — it is remembering to go and look.

A scheduled or goal-driven session can keep working after you close the app, which makes notifications the mechanism that closes the loop: start a long task, put the phone in your pocket, get told when it is done.

One privacy-relevant detail from the enterprise-mode documentation, worth knowing even if you never enable that mode: in enterprise mode, push notifications to phones and browsers carry only a generic title such as “Agent response is ready” — with no message text or session name — while desktop notifications keep the full text. Useful to know if you are ever in an environment where someone else might see your lock screen.

29 · What genuinely works on a phone

An honest list, including the things that are awkward.

Good on a phone

  • Watching progress — which sessions are working, waiting, finished or failed, at a glance.
  • Reading the diff. Seeing what changed, file by file, is the strongest argument for using this interface at all and it translates perfectly to a small screen.
  • Answering a question the agent stopped to ask.
  • Steering. Correcting course, rejecting an approach, adding a constraint.
  • Approving something that needs your say-so.
  • Not being at your desk when the task finishes.

Awkward on a phone

  • Long prompts. Typing a long instruction on a phone keyboard is miserable. Use Voice Mode, or start long tasks from the desktop.
  • Reviewing large diffs. Fine for a small change; genuinely hard for a big one.
  • The terminal. It works, and it has touch controls in the native apps, but it is not a pleasant place to do real work.
  • Element annotation. Point at an element and send the agent its context — that is desktop-only. In a browser tab the panel can display a page but cannot look inside one.
The honest summary: a phone is a monitoring and steering device for OpenChamber, not a development device. That is genuinely useful — most agent work is a long unattended run punctuated by decisions — and it is a different job from the desk.

30 · A phone workflow that is not miserable

A pattern that actually works.

  1. Start long tasks at the desk. Anything involving a long prompt, heavy editing, or a terminal belongs on the desktop. Get it moving, then walk away.
  2. Let it run. If it is goal-driven, it keeps working after you close everything. That is the feature to lean on.
  3. Get told. Notifications tell you it is waiting on you — a question, an approval, a blocked step.
  4. Answer from the phone. Read the diff, answer the question, approve or redirect. This is where the phone earns its place.
  5. Come back for the heavy part. Review properly and commit at the desk.

Underneath that, use Session Goals rather than one-shot prompts. A goal gives the session a finish line, and OpenChamber checks the result after every turn and keeps working until the goal is met, the work is blocked, or it reaches the limit you set. That is what makes unattended running safe to rely on rather than merely possible.

Two supporting features worth knowing: scheduled tasks for genuinely recurring work, and Multi-run when you want the same task attempted by several models at once so you can see which approach actually holds up.

VII When it breaks

31 · Nothing loads at all

Work down this list before anything else.

  1. Open http://localhost:3000 on the computer itself. If that fails, it is not a remote problem and you are debugging the wrong thing. It points at OpenCode connection instead.
  2. Confirm the server is running: openchamber status.
  3. Check the port. If 3000 is taken, OpenChamber should pick another and print it — read the URL it actually printed rather than assuming.
  4. Read the logs: openchamber logs. Most startup failures are a missing OpenCode, a missing Node version, or a port conflict, and all three are usually visible here.
  5. Verify prerequisites: node --version should be 22+, and opencode --version should succeed.

The project keeps a dedicated OpenCode connection troubleshooting page for the cases where OpenChamber starts but cannot reach or start its OpenCode server. Go there rather than working through remote-access issues.

32 · A paired device will not connect

Five causes, in the order worth checking.

  • The QR code or pairing link is single-use. If it was already scanned, or it expired, it is dead. Create a new one from Add a device. This is the most common cause by a wide margin.
  • It was paired as “Home network only”. That device cannot connect from outside that network, ever. Pair it again and choose Anywhere.
  • For an Anywhere pairing, check the relay state at Settings → Remote Instances → OpenChamber Relay on the server. It should say Connected. If it does not, disable and re-enable it.
  • The device was revoked. Its token is gone permanently. Pair it again with a fresh QR code.
  • Local-network reachability. The direct route only works if the server actually listens on the network. If you did not start with --lan, only the relay route works — which is fine, but it explains a direct connection that never falls back.

33 · A tunnel link does not work

Short list, because the causes are few.

  • Run openchamber tunnel status --all to see every tunnel, including ones you may have forgotten.
  • Restart the tunnel from the same instance and port. A tunnel is bound to a port; starting a new mode on the same instance replaces the old one, and a mismatch is a common cause of a link that resolves to nothing.
  • Regenerate the connect link if the previous one was already used. Remember that generating a new one revokes the previous unused link.
  • Check the provider CLI is installed and authenticated. For ngrok that means ngrok config add-authtoken has been run; for Cloudflare that means cloudflared is on your path.
  • Use openchamber tunnel doctor --provider cloudflare to have it check the provider setup for you.
  • Confirm the UI password is set. A tunnel with no password is a public control panel, and the symptom is that the page loads but immediately redirects to a login you were not expecting.

34 · Phone-specific problems

The things that are different on a phone.

  • The PWA will not connect away from home. This is expected and is not a bug. The browser route needs a tunnel; the native apps use the relay. See 17.
  • Keyboard covers the input. The web build is mobile-first with keyboard-safe layouts, so this is usually handled. If it is not, the desktop app has more reliable behaviour.
  • It will not install as an app. You need the browser’s install option, not the OS one. On iOS that is Safari only — Share → Add to Home Screen. Chrome on iOS cannot install a PWA.
  • Android blocks the APK. You must allow installation from that source in your settings when prompted.
  • No background notifications. Both platforms require notification permission. On iOS especially, a web app you have not added to the home screen will not deliver them reliably.
  • Slow on mobile data. A session with a large diff or a long tool output transfers a lot. Paired devices prefer a direct connection when you are on your own Wi-Fi, which is markedly faster than the relay.
  • Typed passwords on a phone keyboard. This is the strongest argument for adding a passkey once it is set up.

35 · Diagnostic commands

The ones worth memorising.

openchamber status                         # is it running at all?
openchamber logs                           # recent output
openchamber stop                           # stop it

openchamber connect-url --qr               # pairing link, this network
openchamber connect-url --relay --qr       # pairing link, works anywhere

openchamber tunnel status --all            # every tunnel, current and past
openchamber tunnel doctor --provider cloudflare
openchamber tunnel providers                # which providers are available
openchamber tunnel stop --port 3000

openchamber startup enable                 # run at login (snapshots env!)
openchamber update                         # update to latest

When something is deeply wrong, setting OPENCHAMBER_VERBOSE_REQUEST_LOGS=1 before starting gives you detailed HTTP logging, and setting OPENCHAMBER_GIT_READ_CACHE_TTL_MS=0 disables the Git-backed file cache if you are chasing a stale-read problem.

VIII Reference

36 · Glossary

Terms used above, in plain English.

Agent
An AI program that carries out tasks on your behalf — reading files, editing code, running commands. OpenCode is the agent; OpenChamber is the interface you watch it through.
Agentic
Describing software that acts on your behalf in multiple steps rather than waiting for a command each time.
API only
Running OpenChamber without serving its browser interface, so only the desktop and mobile apps can connect. A meaningful reduction in attack surface on a server.
Bind address
The network interface a server listens on. 127.0.0.1 means this machine only; 0.0.0.0 means every interface, i.e. anyone who can route to you.
Cloudflared
Cloudflare's command-line tunnel client. OpenChamber drives it to create a public URL.
Diff
A structured view of what changed in your files, line by line. The core reason to use a graphical interface for an agent.
Enterprise mode
A lockdown mode that restricts which model providers, relays and extensions can be used, configured by a policy file or an environment variable. Written for managed work fleets rather than individuals.
End-to-end encrypted
Encryption where only the two endpoints hold the keys. An intermediary can route the traffic but cannot read it.
mDNS
Automatic local network discovery, letting a device be found by name without typing an address. More commonly discussed for OpenCode’s own web server.
Multi-run
Running the same task on up to five models in parallel sessions, so you can compare what each actually produced and keep or fuse the best.
Ngrok
A tunnel provider, like Cloudflare. Requires an account and an authtoken.
OpenCode
The open-source command-line AI coding agent that OpenChamber runs on top of. The two are separate projects and OpenChamber is not affiliated with the OpenCode team.
Pairing
Connecting a second device by scanning a single-use QR code, giving that device its own revocable token rather than sharing a password.
Passkey
A credential tied to Face ID, Touch ID or a hardware key. Stronger and far more practical than typing a password on a phone. Cleared if the UI password changes.
PWA
A Progressive Web App — a web page that installs like a normal application, with its own icon and window. How you get OpenChamber in a phone browser.
Private Relay
OpenChamber’s own relay infrastructure. Your server makes an outbound connection and paired devices reach it through it, end-to-end encrypted, with nothing publicly exposed. The recommended way to use OpenChamber on your own devices away from home.
Reverse proxy
A server you control that sits in front of OpenChamber, handling HTTPS. Recommended if others on your network can reach it, because the built-in connection is plain HTTP.
Session
One ongoing conversation with the agent, including its work, diffs and terminal state.
Session Goals
Giving a session a finish line. The result is checked after every turn and work continues until the goal is met, the agent is blocked, or a limit you set is reached — including after you close the app.
Tunnel
A public URL that forwards to your machine. Convenient and broad, but the provider decrypts traffic at its edge, so it is a real privacy trade.
WSL
Windows Subsystem for Linux. The project recommends running the OpenChamber web server under WSL rather than PowerShell on Windows, for better filesystem access and terminal integration.
Worktree
A separate checkout of a repository, letting an agent work on a branch without disturbing your working directory. Used with Multi-run to run tasks in parallel safely.
